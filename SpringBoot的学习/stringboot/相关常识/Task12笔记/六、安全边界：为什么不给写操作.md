### 6.1 这不是"代码 bug"，是"代码没错但命令错了"
**模型理解错用户意图 + 自信操作 + 无人复核 = 数据没了。**

代码完全按写的执行，每一步都对 —— **错的是"要做什么"这个决定，而它由模型做出。**

### 6.2 四种具体的爆炸方式
**① 参数抽错，删错人**

本项目真实数据：**zhangsan 有两条**（id=1、id=4）。用户说"把 zhangsan 删掉"：

```plain
模型查列表 → 两条 → 挑一条删 → 删了 id=4（用户想删 id=1）
        ↓
无确认、无回收站、物理删除 → 用户连"删错了"都不知道
```

**② 连环调用**

一次请求里可以**连续调用多个工具**。用户说"清理测试数据"：

```plain
getUser → 筛 test001 → deleteUser(8) → 再筛 → deleteUser(11)
```

页面上只显示"已清理 3 条"，**中间发生了什么不看日志根本不知道**。

**③ 语义误判，范围失控**

"清理一下旧数据" → 可能是"30 天前的"，也可能是"没用的"。**它很自信地猜，你没有机会拦。**

**④ 不可撤销，且没有事务保护**

`deleteUser` 没加 `@Transactional`，删一条提交一条。删三条、第二条失败 → **前两条已经没了，不回滚**。

### 6.3 一句话总结
查错了，最坏是答非所问；写错了，是数据真的没了。

所以规矩是"**写操作一律不注册**"，不是"注册了小心点用"。

### 6.4 为什么单独建 UserTools 类（而不是直接标在 ServiceImpl 上）
| 理由 | 说明 |
| --- | --- |
| 职责分开 | service 管业务，tools 管"给模型看的那一层" |
| 爆炸半径小 | `UserServiceImpl` 里还有 add/update/delete，手滑加个 `@Tool` 就暴露了 |
| 好加约束 | 工具层可以只返回部分字段，不影响 service 内部 |


（注意：这里的"爆炸半径"指**误标注解时波及的范围**，跟 6.2 说的"模型误操作的破坏面"是两个层面的东西，别混。）
