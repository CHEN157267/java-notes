第二次请求发出去的 `messages` 有三条，来源各不相同：

| 序号 | role | 谁写进去的 |
| --- | --- | --- |
| ① | `USER` | **用户**（我们转发） |
| ② | `ASSISTANT` | **模型**第一轮的返回（我们原样塞回去） |
| ③ | `TOOL` | **我们的代码**执行后的结果 |


**为什么必须带上前两条**：模型**没有记忆**，每次请求都是全新的。不把 ② 塞回去，它第二次就不知道自己刚要求调过 `getUserById`。

`toolCallId` 的作用是**配对**：模型一次可能要调多个工具，靠这个 id 知道哪个结果对应哪个请求。

**这也解释了"对话越长越贵"**：每一轮都要把前面所有消息重发一遍。工程上的应对（截断 / 摘要 / 按需检索）都是在解决"怎么少发一点但信息不丢"。

### 2.1 `toolCallId` 是什么
**一句话定义**：模型给**这一次工具调用**发的一个单号。

| 维度 | 说明 |
| --- | --- |
| **参照系** | 这一次调用（不是方法、不是用户） |
| **对立项** | 方法名（哪道菜） vs 单号（哪一单） |
| **谁生成** | **模型**（DeepSeek 返回的），我们只是原样回填 |
| **解决什么** | 一次请求里多次调用时，**结果与请求的配对** |
| **常见误解** | 以为是"方法的 ID"、以为是"区分用户的" |


**方法名 vs 单号**：

| | 方法名 | toolCallId |
| --- | --- | --- |
| 例子 | `getUserById` | `call_00_Ahzp3...` |
| 谁定 | 你写的代码 | 模型生成 |
| 变不变 | 永远叫这个 | **每调用一次换一个** |


类比：方法名是"寄到哪家店"，单号是"快递单号"。同一家店寄两次，单号不同。

**为什么需要它 —— 具体例子**

用户说："查一下 id=4 的用户，顺便告诉我一共几个人。"

模型一次返回**两个**调用：

```plain
单号 call_A → getUserById(id=4)
单号 call_B → getUser()
```

执行完，返回**两条** TOOL 消息，各带自己的单号：

```plain
{toolCallId: call_A, content: {id:4, username:"zhangsan"}}
{toolCallId: call_B, content: [10条用户]}
```

模型靠单号对上：**A 是 zhangsan，B 是 10 条**。

**没有单号会怎样**：只能按返回顺序猜。一旦顺序不是它预期的（B 先回来），它就会把"10 条用户"当成 `getUserById(4)` 的结果，回答"id=4 的用户有 10 个人"—— 全错，而且很自信。

**所以核心不是"因为并发"，是"让配对不依赖顺序"**。顺序是最脆弱的东西，协议不愿意依赖它。

**多轮对话里更明显**：第三轮时，messages 里可能已经躺着好几组工具调用的记录。靠单号才能分清哪份结果属于哪一轮的哪个请求。

⚠️ **一处未实测**：我们项目在"一次请求多个工具"时到底是顺序执行还是并发执行，**没验证过**。Spring AI 的 `DefaultToolCallingManager` 默认是顺序 for 循环，并发需要额外配置。**但这不影响结论** —— 无论哪种，协议都用单号而不是位置来配对。

**这也解释了"对话越长越贵"**：每一轮都要把前面所有消息重发一遍。工程上的应对（截断 / 摘要 / 按需检索）都是在解决"怎么少发一点但信息不丢"。
