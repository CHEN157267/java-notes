### 1 现在这个接口的局限
`/ai/chat` 只能"凭模型自己知道的东西"回答 —— **它看不到你的数据库、你的笔记**。

### 2 RAG 四步
```plain
① 切分     把文档切成小段（chunk）
② 向量化   每段用 Embedding 模型变成一串数字（语义坐标），存进向量库
③ 检索     用户提问 → 同样向量化 → 算相似度 → 取最相似的 Top-K 段
④ 生成     把"检索到的段落 + 用户问题"拼进提示词 → 模型基于它们回答
```

### 3 三个关键认知
**① 向量不是二进制，是"语义坐标"**

```plain
"今天下雨了"  → [0.23, -0.11, 0.87, ...]   ← 1536 个小数
"外面在下雨"  → [0.22, -0.09, 0.85, ...]   ← 很接近
"我想吃火锅"  → [0.91,  0.55, -0.32, ...]  ← 差很远
```

**意思相近 → 坐标相近 → 可以用数学算距离。**

**② 检索不是"字符串匹配"，是"算相似度"**

+ 用户问"怎么重置密码"，文档写"忘记密码的处理流程" → **字面一个词都不重合**，关键词搜索直接失败
+ **向量能抓到**（语义坐标近）→ 这才是 RAG 比关键词搜索强的地方

**③ 拼提示词确实是"我们在代码里拼"**

```plain
String prompt = """
        你是客服助手。以下是参考资料：
        %s
        用户问题：%s
        请只根据上面的资料回答，资料没有的信息就说"不知道"。
        """.formatted(retrievedDocs, q);
```

**要准备几个模板**（不同场景用不同模板）。

### 4 Embedding 是什么
**另一类模型**（不是 GPT 那种"写文字"的）：

+ **Embedding 模型**：只干一件事 —— **把文字变成向量**
+ **生成模型**（GPT 系列）：**根据上下文写文字**
+ **RAG = 前者检索 + 后者生成**

**必须用同一个 Embedding 模型**做"资料向量化"和"提问向量化" —— 否则坐标系不一样，没法比。

**可用的**（【未逐个查证】）：

+ 在线 API：OpenAI `text-embedding-3-small`、通义 `text-embedding-v3`、智谱 `embedding-2`
+ 本地开源：**BGE 系列**（`bge-m3`）、`m3e`、sentence-transformers

**时间线**（【我的记忆，未逐一查证】）：word2vec（2013）比 GPT-1（2018）**早 5 年** —— "把文字变向量"和"生成文字"是两条不同的技术路线。
