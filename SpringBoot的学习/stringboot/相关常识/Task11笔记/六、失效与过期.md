### 6.1 为什么必须主动删
TTL 30 秒 ≠ "数据变了 30 秒后才对"。写操作之后，缓存里还是**旧数据**，最长会脏 30 秒。

```plain
private void evictCache(String key) {
    try {
        stringRedisTemplate.delete(key);
    } catch (DataAccessException e) {
        log.warn("Redis旧缓存删除失败，{}", e.getMessage());   // 降级：不影响业务
    }
}
```

三个写方法在**成功后**调用它：`addUser` / `updateUser` / `deleteUser`。

**为什么 add 也要删？** 缓存存的是**整张表的快照**，新增一个人，这份快照就少一条 —— 用户刷新看到的还是旧列表。

### 6.2 删的时机：必须在成功之后
**实测过的一个坑**：把 `delete` 写在方法开头，会怎样？

```plain
DELETE /user/delete/999999  →  404（库里没这条）
之后查 Redis  →  keys 为空 —— 缓存被白清了一次
```

顺序错了：业务失败也清缓存。正确位置是"操作成功"的分支里。

### 6.3 过期是怎么"删"的：两种策略
| 策略 | 做法 |
| --- | --- |
| **惰性删除** | 这个 key 被访问时才检查是否过期，过期才删 |
| **定期删除** | 默认每 100ms 随机抽 **20 个**过期字典里的 key，删掉过期的；若过期比例 > **25%**，立刻再抽一轮 |


结论：**过期 ≠ 准时删**。零星过期的 key 可能滞留一阵（占内存、但读不到）；大量同时过期时清得快。

### 6.4 命中率
**命中率 = 命中次数 ÷ 总请求次数**。它比"缓存里有多少条数据"更能说明价值 —— 存一万条没人查，命中率依然是 0。
