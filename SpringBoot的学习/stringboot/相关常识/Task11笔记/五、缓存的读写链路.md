### 5.1 代码主干（`UserServiceImpl.get   User()`）
```plain
String json = stringRedisTemplate.opsForValue().get("user:list");   // ① 先查缓存
if (json != null) {
    log.info("缓存命中：从 Redis 读取用户列表");
    return objectMapper.readValue(json, new TypeReference<List<User>>() {});   // ② 命中：反序列化
}

List<User> result = userMapper.selectList(null);                    // ③ 未命中：回源
stringRedisTemplate.opsForValue().set("user:list",
        objectMapper.writeValueAsString(result), Duration.ofSeconds(30));     // ④ 写回 + TTL
log.info("缓存未命中：回源查库并写入缓存");
return result;                                                      // ⑤ 直接返回，别再读回来
```

### 5.2 key 的命名
`user:list` —— 约定 `**业务:资源**`。验收要求"能解释 key 怎么命名"，`users` 解释不出层次，`user:list` 一眼就懂。

### 5.3 ★ 序列化：一遍搞清四个概念
| 概念 | 方向 | 产物/输入 |
| --- | --- | --- |
| **序列化** | 对象 → 文本 | `writeValueAsString(user)` → **String** |
| **反序列化** | 文本 → 对象 | `readValue(json, 类型)` → **对象** |


三个必须记住的：

1. `**write**`** 是"写出去"（写成字符串），**`**read**`** 是"读回来"（读成对象）** —— 跟数据库的读/写无关，Jackson 不知道数据库存在。
2. **String 就是 JSON**。JSON 是文本格式，在 Java 里的天然载体就是 `String`；不存在"先转 String 再转 JSON"。对比：JDK 序列化产出的是 `byte[]`。
3. **泛型擦除 → 必须 **`**TypeReference**`。`List.class` 只说"是个列表"，元素类型被擦掉了，Jackson 会给你 `List<LinkedHashMap>`；`new TypeReference<List<User>>() {}` 是把泛型信息"刻"进匿名子类的字节码里，让它反射读得到。

### 5.4 ★ 序列化/反序列化对类有什么要求
| 方向 | 默认需要什么 | 为什么 |
| --- | --- | --- |
| 序列化 | **getter** | Jackson 要靠它**从对象里取值**，才能写进 JSON |
| 反序列化 | **无参构造器 + setter** | 先 `new` 一个空对象，再逐个字段 `set` |


**JSON 文本里只有键值对，没有"这是 User 类"这种信息** —— 所以进 Java 那一刻，必须由你告诉它目标类型。

（以上是**默认行为**，能改：public 字段也能被发现；`record` 或 `@JsonCreator` 可以用构造器反序列化。）

### 5.5 ★ 项目里有两次序列化，别混
| 时机 | 谁做的 | 用什么 |
| --- | --- | --- |
| 存/取 Redis | **你手写**的 `objectMapper` | 构造器注入的那个 Jackson `ObjectMapper` |
| 返回给前端 | **Spring MVC 自动**（HttpMessageConverter） | Spring 内置的 `ObjectMapper` |


`Result` 只是普通 POJO，**它自己不会变成 JSON**；真正的转换发生在你 `return` 之后，Spring 把它序列化再写进响应体。

**顺手纠正一个归属**：`ObjectMapper` 是 **Jackson** 的，不是 MyBatis-Plus 的 —— Plus 只管数据库，一辈子不碰 JSON。

### 5.6 ★ 两个注解：密码为什么要有两道关
`password` 字段上现在挂了三层保护，各管一段路，**缺一个就漏**：

```plain
@NotBlank                                    // ① 校验：进来时不能为空
@Pattern(regexp = "[_a-zA-Z0-9]{6,20}")      // ② 校验：格式
@JsonProperty(access = WRITE_ONLY)           // ③ 序列化：写进来可以，写出去不行
@TableField(select = false)                  // ④ 查询：别把这一列从库里捞出来
private String password;
```

| 注解 | 管的方向 | 效果 | 缺了会怎样 |
| --- | --- | --- | --- |
| `@TableField(select = false)` | **数据库 → 对象** | SQL 里不带 `password` 列 | 每行密码被查进内存、被 MyBatis 日志打出来 |
| `@JsonProperty(WRITE_ONLY)` | **对象 → JSON** | 序列化时跳过；**反序列化照收**（前端提交的密码能进来） | `add`/`update` 返回的对象里带着 BCrypt 哈希，直接吐给前端 |


**为什么两个都要**（这是最容易想错的地方）：

+ 查出来的对象：因为 `@TableField`，密码本来就是 `null` → 只靠它也不会漏；
+ **但 **`**add**`** 返回的那个对象不是查出来的**，它是 `insert` 之后**内存里的那一个**，密码有值。这时候拦住它的是 `@JsonProperty`。

实测证据（2026-11-07）：`POST /user/add` 返回

```plain
{"data":{"id":19,"username":"cachelogin","createTime":null},"code":200}
```

—— 没有 `password`。而这个对象的密码字段是有值的，全靠 `@JsonProperty` 挡掉。

**记忆口径**：`TableField` 管"**别从库里拿**"，`JsonProperty` 管"**别往外说**"。两个方向，两个动作，不能互相替代。

**副作用**：`select = false` 之后，任何查询都拿不到密码 —— 以后做登录校验，要么单独写一个带列的查询，要么另想办法。
