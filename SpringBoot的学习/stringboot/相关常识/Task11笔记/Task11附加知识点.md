## 一、Java IO：一张四象限表
### 1.1 两个维度，四个基类
| | 输入（读进程序） | 输出（从程序写出） |
| --- | --- | --- |
| **字节流**（`byte`） | `InputStream` | `OutputStream` |
| **字符流**（`char`） | `Reader` | `Writer` |


### 1.2 ★ 方向的参照物是"你的程序"，不是文件
这一点最容易搞反。你原来的想法是"一开始没有数据，所以要写入；后来有了，就读出来" —— 那是**文件的生命周期**，不是 IO 的方向。

| 词 | 谁的角度 | 实际动作 |
| --- | --- | --- |
| **输入（Input / read）** | 程序的 | 数据**流进**程序内存 |
| **输出（Output / write）** | 程序的 | 数据**流出**程序内存 |


所以"读文件"是输入（磁盘 → 程序），"写文件"是输出（程序 → 磁盘）。跟文件里有没有内容无关。

### 1.3 ★ 字节流"看得懂英文"吗？—— 它什么都不懂
**字节流只认数字 0~255**，它不知道什么叫"字符"。

+ 英文 `A` 在 ASCII / UTF-8 里正好是 **1 个字节**（65）
+ 所以用字节流读英文，"一个字节 = 一个字母"**碰巧**成立
+ 但读中文就崩：UTF-8 里"中" = `E4 B8 AD`**3 个字节**，按字节读会被劈成三个乱码

**它读到的是 **`**72**`**（数字），你得自己 **`**(char) 72**`** 才变成 **`**H**`**。** 所谓"看得懂英文"，是数字和字母在 ASCII 里恰好一一对应造成的错觉。

**所以"老外不用字符流"是错的**：Java 的 `String` 是 UTF-16 的 `char` 序列，任何语言的文本，从字节到 `char` 都要解码。老外写 `FileReader` 一样多。

### 1.4 字符流 = 字节流 + 解码器
准确说法不是"有了 UTF-8 表的字节流"，而是：

**字符流 = 字节流 + 一个解码器（**`**CharsetDecoder**`**），按指定字符集把字节序列还原成 **`**char**`**。**

**解码器是在"真的做转换"，不是"只告诉含义"**：

```plain
字节 E4 B8 AD  →  解码器  →  Unicode 码点 U+4E2D  →  char '中'
```

### 1.4.1 ★ 解码器怎么知道"哪几个字节是一个字"——UTF-8 是自描述的
这是最关键的一问：**没有分隔符**，靠的是每个字节头部的二进制位自己说明身份。

| 首字节长什么样 | 这个字符占几个字节 | 说明 |
| --- | --- | --- |
| `0xxxxxxx` | 1 字节 | 就是 ASCII（英文/数字/符号） |
| `110xxxxx` | 2 字节 | 后跟 1 个 `10xxxxxx` |
| `1110xxxx` | 3 字节 | 后跟 2 个 `10xxxxxx`（大部分汉字） |
| `11110xxx` | 4 字节 | 后跟 3 个 `10xxxxxx`（emoji、生僻字） |


**规则两条**：

1. **首字节的高位决定后面跟几个字节**；
2. **所有续字节（非首字节）都必须以 **`**10**`** 开头**。

所以解码器读到 `E4`（`11100100`）就知道"这是 3 字节的首字节"，接着读两个以 `10` 开头的字节即可。

**你担心的"解错一个会不会后面全错"**：UTF-8 里**基本不会**。因为续字节必须以 `10` 开头，一旦对齐错位，下一个字节大概率不满足 `10` 前缀 → **立刻能发现**，而不是"悄悄解成乱码还继续"。这也是 UTF-8 比 GBK 抗损坏的原因之一（GBK 的两个字节都可能落在合法范围，错位后不容易察觉）。

### 1.4.2 GBK 与 UTF-8：不是"看不看得懂中文"
| | GBK | UTF-8 |
| --- | --- | --- |
| 出身 | 中国国家标准（GB2312 的扩展） | **Unicode 的一种编码**（国际标准） |
| 覆盖 | 中文 + 英文字母数字 + 少量符号 | **全世界所有字符**（含日韩、阿拉伯、emoji） |
| 汉字占几字节 | **2 字节** | **3 字节**（少数 4 字节） |
| 英文字母 | 1 字节 | 1 字节 |
| 能否自描述 | ❌ 不能（错位难发现） | ✅ 能（见上一节） |


**纠正一个说法**：不是"GBK 看不懂中文"——**GBK 懂中文，但它不懂韩文、阿拉伯文、emoji**，出了东亚圈就没辙。UTF-8 是"什么都懂"。

一句话：**GBK 是"中文专用字典"，UTF-8 是"世界通用字典"**。所以项目里统一用 UTF-8，不是因为它"更懂中文"，而是因为它**不会遇到字典里查不到的字**。

### 1.51 ★ 码点 / 编码 / 索引：三个最容易混的东西
| 概念 | 是什么 | 例子 |
| --- | --- | --- |
| **码点（code point）** | Unicode 给每个字符分配的**唯一编号**，全世界唯一 | `A` = 65、`中` = 20013（U+4E2D）、`😀` = 128512 |
| **编码（encoding）** | 把这个编号**存成字节**的规则 | `中` 在 UTF-8 = `E4 B8 AD`；在 GBK = `D6 D0` |
| **索引（index）** | 它在字符串里**排第几个** | `"中文".charAt(0)` 取到 `中` |


**两个最常见误解**：

1. **"码点会随编码变"** ❌ —— **码点是 Unicode 定的，跟编码无关**。`中` 的码点永远是 20013，UTF-8 只是把它存成 3 个字节、GBK 存成 2 个字节。换个编码，**字节变了，码点没变**。
2. **"码点像索引"** ❌ —— 码点是"身份证号"，索引是"座位号"。`"中文".charAt(0)` 是索引（第 0 个），`'中'` 的码点是 20013（身份）。

**为什么容易混**：ASCII 范围（0~127）里，码点和那个数字恰好是同一个值（`A` 既是 65 也是码点 65），所以感觉像"值本身"。到了中文（20013）就露馅了。

`**read()**`** 返回 **`**-1**`：那不是"结尾字符的码点"，而是**流结束的标记**（EOF）—— "没有下一个字符了"，跟码点无关。

### 1.52 编码表谁定？—— 你不写，它就用默认值
| 写法 | 用哪个编码 |
| --- | --- |
| `new InputStreamReader(in, StandardCharsets.UTF_8)` | 你指定的 ✅ 推荐 |
| `new InputStreamReader(in)` | **平台默认**（`file.encoding`） |


【实测·本机 JDK 21，2026-11-09】

```plain
file.encoding    = UTF-8      ← Java 读文件的默认编码（Java 18 起强制 UTF-8）
native.encoding  = GBK        ← 操作系统本地编码（中文 Windows）
sun.jnu.encoding = GBK        ← 文件名/路径用的编码
```

所以：**Java 18+ 默认是 UTF-8，但这台机器的系统编码仍是 GBK** —— 这三个值各管一段，别混。

**实践铁律：涉及文本读写，永远显式指定 **`**StandardCharsets.UTF_8**`**。** 不然换台机器、换个系统就乱码，而且这种 bug 极难查（表现是"偶尔几个字变问号"）。

### 1.61装饰器套娃：每一层只加一种能力
```plain
BufferedReader br = new BufferedReader(
        new InputStreamReader(
                new FileInputStream("a.txt"), StandardCharsets.UTF_8));
```

从里往外，各管一段：

| 层 | 干的事 |
| --- | --- |
| `FileInputStream` | **真正碰文件的**：向操作系统要字节（一次读一批） |
| `InputStreamReader` | 把字节**解码**成字符 |
| `BufferedReader` | 加**缓冲** + 提供 `readLine()` |


**你猜"最里面那个只是给壳"—— 反了**：最里面那个才是唯一真正读磁盘的，外面两层都只是在它给的字节上做加工。

**缓冲到底有什么用**（你说不理解）：

没有缓冲：每读一个字符，就向操作系统发一次请求（系统调用）。 有缓冲：一次向系统要 8KB，剩下的都从内存取。

系统调用要切换内核态，一次开销是普通内存访问的上千倍。一个 1MB 的文本，没缓冲要发上百万次请求。**这就是缓冲的全部意义：把"多次小请求"变成"一次大请求"。**

比喻：喝水，一杯一杯去接 vs 先接一桶放旁边。

**注意方向**：`BufferedReader` 包的是**字符流**（Reader），不是"字符流包字符流包字节流"—— 从外到里是 `BufferedReader(Reader) → InputStreamReader(Reader, 内部持有 InputStream)`。它同时实现了 `Reader` 接口并持有字节流，所以看起来像"字符套字符套字节"。

### 1.62 ★ 纠正：`Reader.read()` 返回的是 **UTF-16 编码单元**，不是码点
我之前说"`read()` 返回一个字符的码点"—— **不够严谨，要改**。

严格说法：`**Reader.read()**`** 返回一个 **`**int**`**（0~65535），代表一个 **`**char**`** 的值，也就是一个 UTF-16 编码单元（code unit）。**

两者什么时候相同、什么时候不同：

| 字符 | 码点 | `char` 值 | 一致吗 |
| --- | --- | --- | --- |
| `A` | 65 | 65 | ✅ 一样 |
| `中` | 20013 | 20013 | ✅ 一样（在 BMP 基本平面内） |
| `😀` | **128512（U+1F600）** | 先 `55357`（0xD83D）再 `56832`（0xDE00） | ❌ **一个码点要两次 **`**read()**` |


**原因**：`char` 只有 16 位，最大 65535；而 Unicode 范围到 1114111（0x10FFFF）。超出 65535 的字符（emoji、部分生僻字）**一个字符用两个 char 拼起来**（代理对 surrogate pair）。

【实测·JDK 21，2026-11-12】`"A😀中"`：

```plain
length() = 4          ← 4 个 char（不是 3 个字！）
charAt(1) = 0xD83D    ← 代理对的前半
charAt(2) = 0xDE00    ← 代理对的后半
codePointAt(1) = 128512   ← 真正的码点
codePointCount = 3        ← 真正的字符数
```

**所以两句话记住**：

1. `read()` / `charAt()` 给的是 **UTF-16 单元**（可能只是半个字）；
2. 要真码点，用 `**codePointAt()**`；要真字符数，用 `**codePointCount()**`。

**这也是"索引不等于字符位置"的根源**：`"A😀中".length()` 是 4，但肉眼只看到 3 个字 —— 因为那个 emoji 占了两个 char。

### 1.7 现代写法：`Files` 一行搞定
```plain
String text       = Files.readString(Path.of("a.txt"));          // 一次读完，UTF-8
List<String> lines= Files.readAllLines(Path.of("a.txt"));        // 按行读
Files.writeString(Path.of("b.txt"), "hello");                    // 写出
```

**为什么看不到"字符流/字节流"**：Java 11 的 `Files.readString` 内部**就是**那一套套娃，只是帮你写好了、还帮你关了。

底层没变，只是被封装了。"看不见"不等于"没发生" —— 这是读框架代码时要一直记得的一条。

### 1.8 速记
| 我要处理 | 用什么 |
| --- | --- |
| 文本文件（txt/json/csv） | 字符流（`Reader`/`Writer`）或 `Files.readString` |
| 图片/音频/视频/压缩包 | 字节流（`InputStream`/`OutputStream`） |
| 不确定 | 看它有没有"编码"这回事：有 → 字符流 |

## 二、内存与显存：数据都住在哪
### 2.1 一条阶梯（详见 Task11 笔记 §2.4）
```plain
磁盘 → 内存（含 OS 页缓存）→ CPU 缓存 → 寄存器
```

每一层都是左边那层的副本，越往右越快、越贵、越小。

### 2.0 先搞清"内核"是什么（它是软件，不是硬件）
**内核（kernel）= 操作系统最核心的那部分程序**，开机后一直跑在最高权限（内核态），直接管硬件。

| 它管什么 | 具体干的事 |
| --- | --- |
| **进程调度** | 决定哪个程序先用 CPU、用多久 |
| **内存管理** | 分配/回收内存，做页缓存，虚拟内存 |
| 设备驱动 | 读写磁盘、网卡、键盘 |
| 系统调用 | 提供"程序请求内核干活"的唯一入口（`read()`、`write()` 本质都是求内核） |


所以你说的"内核是操作系统里划分内存的那个软件" —— **基本对**，只是它管的远不止内存。

⚠️ **"内核"这个词被借用了两次，别混**：

| 说法 | 指的是 | 例子 |
| --- | --- | --- |
| **操作系统内核** | OS 的核心程序 | Linux kernel、Windows NT kernel |
| **浏览器内核** | 浏览器里"解析并渲染网页"的引擎 | Edge 里的 Chromium（以前的 IE 用的是 Trident） |


两个"内核"完全不是一个东西，只是中文翻译撞了名。**你记得"Edge 里有 IE 内核"—— 那说的是渲染引擎**（Edge 早期用的 Trident/EdgeHTML，现在换成了 Chromium）。

**页缓存归操作系统内核管**，不是某个进程 —— 这就是它"看不见摸不着，但一直在工作"的原因。

### 2.2 显存（VRAM）是什么
**显存 = 显卡自己的一块内存**，和主板上的内存（RAM）物理上是两个东西。

| | 内存（RAM） | 显存（VRAM） |
| --- | --- | --- |
| 插在哪 | 主板 | **显卡板上** |
| 谁用 | CPU + 所有程序 | **GPU** |
| 特征 | 容量大（16/32 GB）、带宽中等 | 容量小、**带宽极高**（几百 GB/s） |
| 存什么 | 程序、对象、页缓存 | 纹理、顶点、帧缓冲、着色器 |


**为什么 GPU 需要独立显存**：GPU 有几千个核心同时干活，同一帧要并发访问海量纹理。走主板内存（PCIe 通道）带宽不够、延迟太高 —— 所以显存贴着 GPU 放。

### 2.3 8 GB 是显存吗 —— 是
你的 **RTX 4060 Laptop 8GB**，这个 8GB 就是**显存容量**（不是内存，也不是"8 代"）。

**爆显存会发生什么**（比"显卡不干了"更常见的是"降级硬撑"）：

1. 显存放不下 → 驱动把一部分数据挪到**系统内存**（Windows 叫"共享 GPU 内存"），走 PCIe 来回搬；
2. 带宽差一个数量级 → **帧率暴跌、贴图变糊、卡顿**；
3. 极端情况 → 驱动超时重置（TDR），**游戏崩溃**、黑屏几秒。

所以"爆显存"通常是"先卡到不能玩，再崩"，不是"瞬间罢工"。

### 2.4 玩游戏时，同一份数据在四层各有一份
| 层 | 游戏里发生什么 |
| --- | --- |
| 磁盘 | 游戏本体躺在硬盘（几十 GB） |
| **OS 页缓存** | 读地图文件时，内核顺手留在内存里 → 下次回这张图几乎不读盘 |
| **进程内存** | 当前地图的贴图/模型/音频解压后放进程堆里 |
| **显存** | 要渲染的纹理传到 GPU 显存（显存不够就掉帧） |


**这就是"层次"最直观的例子**：同一个贴图，在四个地方各有一份，越靠近 GPU 越快越贵。

## 三、网络基础（够用版）
### 3.1 IP、掩码、网段
+ **IP**：`192.168.1.5` —— 一台机器在网络里的门牌号。
+ **子网掩码**：`255.255.255.0`（常写成 `/24`）—— **本身也是 4 段**，不是"IP 后面那个数字"。它标记"IP 的哪几位是网络号"：`/24` = 前 24 位（前三段）是网络号，剩下的位数给主机。
+ **网段**：把 IP 和掩码**按位与**算出来的结果。

**网段到底怎么算**（这就是你不知道的那一步）：

```plain
IP    192.168.1.5   →  11000000 10101000 00000001 00000101
掩码  255.255.255.0 →  11111111 11111111 11111111 00000000
按位与 ────────────────────────────────────────────────────
网段  192.168.1.0   →  11000000 10101000 00000001 00000000
```

**规则**：掩码里是 `1` 的位 → 照抄 IP；是 `0` 的位 → 归零。剩下的部分就是"主机号"。

所以"前三段相同就是同一个网"只在 `/24` 成立 —— 它是**算出来的结论**，不是定义。换成 `/16`（`255.255.0.0`），就是前两段相同才算同网。

**主机号的边界**（回答你那个"有上限吗"）：

| 一个 `/24` 网段（192.168.1.x） | 能不能用 |
| --- | --- |
| `.0` | ❌ 网络地址（代表"这个网"本身） |
| `.1 ~ .254` | ✅ 可分配给机器 → **最多 254 台** |
| `.255` | ❌ 广播地址（发给全网段所有机器） |


**"超过 254 台怎么办"**：换更大的网段 —— 用 `/23`（`255.255.254.0`，能容纳 510 台），此时 `192.168.0.x` 和 `192.168.1.x` 属于**同一个网**。所以不是"超过编号就不算同一个网"，而是"网段大小由掩码决定，掩码换了，边界就换了"。

**IP 是"自动给的"吗**：多数情况下是路由器用 DHCP 自动分配，也可以手动设静态 IP。至于"能不能从 IP 看出地理位置" —— 公网 IP 可以粗略定位到城市（GeoIP 库），**内网 IP 完全看不出来**（`192.168.x.x` 是私有地址，全世界重复使用）。开代理时看到的是代理的 IP，所以位置会失真。

### 3.2 网关
**网关 = 这个局域网的出口**（通常是路由器，如 `192.168.1.1`）。

+ 同一个网段内通信：直接发，不用网关；
+ 跨网段（比如访问外网）：**全部交给网关转发**。

所以配网络时那三件套是：**IP + 掩码 + 网关**。少一个，要么上不了网，要么只能局域网内玩。

### 3.3 端口与防火墙
+ **IP 定位机器，端口定位程序**。Redis 默认 **6379**，MySQL 3307，我们的 Spring Boot 8080。
+ **防火墙**是"门卫"：默认拦掉大部分外来连接，只放行你允许的端口。**没放行 = 外面连不进来。**

### 3.4 "同一个局域网"不等于"能互相访问"
两点常见坑：

1. **AP 隔离**：很多校园网/公共 WiFi 开了"设备隔离"，同一个 WiFi 下的两台电脑也 ping 不通；
2. **方向性**：你能连别人，不代表别人能连你（防火墙、NAT）。

所以"局域网能连"要实测：`ping` 通 + 端口通（`telnet IP 6379`）才算数。

## 四、Redis 的连接与认证（把上面串起来）
### 4.1 三件事都得满足才能连上
| # | 条件 | 配在哪 |
| --- | --- | --- |
| 1 | Redis 的 `bind` 允许这个来源地址 | **服务端 **`**redis.conf**` |
| 2 | 防火墙放行 6379 | 操作系统防火墙 / 云安全组 |
| 3 | 密码（或 ACL 账号）正确 | 服务端 `requirepass`/ACL；客户端 `spring.data.redis.password` |


**同一件事两边都要写**：服务端是"我要求密码"，客户端是"我提交密码"。

### 4.2 客户端只写密码，Redis 怎么知道"我是谁"
因为 Redis 6+ 里有一个**内置用户叫 **`**default**`。你不写用户名 → 就是用它。

```plain
spring.data.redis.password=xxx          # 用 default 用户
spring.data.redis.username=cacheuser    # 指定其他 ACL 用户时才有这行
```

所以不是"一个个试"，是 **用户名（默认 **`**default**`**）+ 密码** 一起校验。

### 4.3 ★ ACL 的"多用户"是什么，不是什么
| ✅ 是 | ❌ 不是 |
| --- | --- |
| **Redis 服务端**可以有多个账号 | 客户端多开几个连接 |
| 每个账号限定**能跑哪些命令**（如只给 `GET/SET`） | 每个账号有自己独立的一份数据 |
| 每个账号可限定**能访问哪些 key 前缀**（如只给 `user:*`） | 数据按账号隔离 |


**数据是全局的**，一个 Redis 里只有一个 key 空间；账号只决定"你有权碰哪些"。这跟数据库"每个用户一个 schema"不是一回事。

### 4.4 网段限制怎么写
`redis.conf` 的 `bind` 只能写**具体 IP**，不支持 `192.168.1.0/24` 这种网段写法。所以实践是：

+ `bind 127.0.0.1` → 只允许本机（默认，最安全）
+ `bind 0.0.0.0` → 所有网卡都听（**必须配密码 + 防火墙**）
+ `bind 192.168.1.5` → 只听这一个网卡

**网段/来源限制交给防火墙**：只放行 `192.168.1.0/24` 访问 6379，比在 Redis 里限制更靠谱。

⚠️ **公网裸奔的 Redis 是最经典的入侵入口**（被扫到就中挖矿）。所以"内网 + 密码 + 防火墙"三条缺一不可。

## 五、一句话收
| 问题 | 一句话 |
| --- | --- |
| IO 方向看谁 | 看**程序**：进来是输入，出去是输出 |
| 字节流懂英文吗 | 不懂字符，只认数字；英文一字节是**巧合** |
| 字符流是什么 | 字节流 + 解码器；编码不指定就用系统默认 |
| 缓冲有什么用 | 把"多次小请求"合并成"一次大请求" |
| `Files.readString` 为什么简单 | 套娃没消失，只是被封装了 |
| 页缓存是谁的 | 内核的，不是进程的；按 4KB 页 |
| 8GB 是什么 | 显存；爆了先卡再崩（借系统内存） |
| 网段怎么判断 | IP + 掩码算出来；/24 就是前三段相同 |
| 网关是什么 | 局域网的出口，跨网段必经 |
| ACL 多用户 | 多个账号，权限不同；**数据不隔离** |
