### 2.1 一句话
Redis 是一个跑在独立进程里的 `Map<String, byte[]>`，所有连上来的客户端都能读写。

创建、扩容、回收全由 redis-server 这个进程负责 —— 我们一行创建代码都没写，只是通过网络发 `SET / GET / DEL`。

### 2.2 为什么不用本地 `Map` 当缓存
| 理由 | 说明 |
| --- | --- |
| **多进程/多机器共享** | 部署两台机器时，A 缓存的用户在 B 看不见，各查各的库 |
| **不占 JVM 堆** | `Map` 存几十万对象会撑爆堆 → GC 频繁 → OOM 把服务弄死 |
| **过期与淘汰由中间件管** | `Map` 要自己写定时清理，还得处理并发；Redis 一句 `EXPIRE` 就有，还带 LRU |
| **可选持久化** | 服务重启，缓存还在（因为它本来就不在服务进程里） |


**注意**："更快"不算理由 —— 单机比速度，`HashMap` 甚至更快（没有网络往返）。

### 2.3 缓存的三层，别混
| 层次 | 例子 | 容量 | 断电/重启 | 能否跨机共享 |
| --- | --- | --- | --- | --- |
| 硬件缓存 | CPU 的 L1/L2/L3 | KB ~ MB | 没了 | 不能 |
| 进程内缓存 | Java 的 `HashMap` | 受 JVM 堆限制 | 进程停就没 | 不能 |
| 分布式缓存 | **Redis** | GB 级 | 默认也没（可配持久化） | **能** |


磁盘缓存（浏览器/App 的"清缓存"）不属于上面任何一层 —— 它是"**远端的慢数据**复制到**本地磁盘**"，快的那一端是硬盘不是内存。缓存的定义不是"内存"，而是**把慢的复制到快的**。

### 2.4 ★ 把五层串成一条链（别当成排名）
上面那张表容易让人以为是"五个并列的类别"。其实它们是**一条速度阶梯**：

```plain
网络  →  磁盘  →  内存  →  CPU 片内
（最慢）                      （最快）
```

**每一层都是"左边那层的缓存"**，具体是：

| 缓存 | 慢的一端（数据原本在哪） | 快的一端（副本放哪） | 谁在管 |
| --- | --- | --- | --- |
| CPU 缓存（L1/L2/L3） | 内存 | CPU 片内 SRAM | CPU 硬件 |
| **OS 页缓存（page cache）** | 磁盘 | 内存 | **操作系统** |
| 进程内缓存（`HashMap`） | 数据库 / 文件 | JVM 堆（内存） | 你的代码 |
| Redis | 数据库 | 独立进程的内存 | Redis 自己 |
| 浏览器 / App 缓存 | 网络（远端服务器） | **本地磁盘** | 浏览器 / App |


关键理解：同一个东西，在上层眼里是"快"，在下层眼里是"慢"。

内存对 CPU 缓存来说是"慢的一端"，对磁盘来说又变成"快的一端"。 所以"层次"不是"谁比谁高级"，而是链式接力：把左边搬到右边，越往右越快、越贵、越小。

你之前漏掉的正是中间那层 **OS 页缓存**：你读一个文件读两遍，第二遍快很多，不是文件变了，是操作系统把文件内容留在了内存里。

**"自动清理"不是 Redis 的专利**（这一条要纠正）：

| 缓存 | 满了怎么办 |
| --- | --- |
| CPU 缓存 | 硬件自动换出（你无法干预） |
| OS 页缓存 | 内存紧张时操作系统自动回收 |
| 浏览器缓存 | 有容量上限 + 过期时间，超了淘汰旧的 |
| 进程内 `HashMap` | **不自动** —— 要自己写清理，写漏了就 OOM |
| Redis | `maxmemory` + 淘汰策略 + **TTL** |


Redis 真正独特的地方不是"会自动清"，而是**"过期时间是一等公民"**（`EXPIRE` 一句话就有），这也是它能当缓存用的根本原因。
