因为 **HTTP 状态码和业务状态码，描述的是两个不同层面的东西**。

| | HTTP 这一层 | 业务这一层 |
| --- | --- | --- |
| 关注什么 | 这次**交互**成不成 | 这次**操作**对不对 |
| 成功标志 | 请求送达、处理完毕、响应完整发出 → **200 OK** | 操作按预期完成 |
| 失败标志 | 连接断了 / 服务挂了 / 根本没响应 | 参数不合格 → 400；用户名重复 → 409 …… |
| 放在哪 | 响应**首行**：`HTTP/1.1 200` | 响应 **body** 里的 `code` 字段 |


打个比方：**邮局只管信寄到了没有，不管信里写的密码是 6 位还是 3 位。**

+ 信寄到了 → HTTP 200
+ 信里的密码写错了 → 业务 400

两件事不冲突。

所以 advice 返回 `Result` 时，**这一次 HTTP 交互本身是完美成功的**——请求收到了、异常处理了、响应发出去了。200 说的是这件事。至于"参数不合格"，由 body 里的 `code = 400` 去说。

⚠️ 这是**团队约定**（HTTP 统一 200 + 业务码放 body），**不是技术必然**。 另一种流派认为"400 就该是 HTTP 400"，更贴近 REST 规范。我们项目选前者，因为前端只需要判断 body 里一个地方。

如果哪天真想让 HTTP 也变成 400：在 `@ExceptionHandler` 方法上加 `@ResponseStatus(HttpStatus.BAD_REQUEST)`，或者直接返回 `ResponseEntity.status(400).body(...)`。
