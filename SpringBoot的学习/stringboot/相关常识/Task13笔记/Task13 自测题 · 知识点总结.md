## 二、Q4：那个手法叫“用户名枚举”
你猜的“模糊信息法”不算 —— 它不是这个领域的术语。准确名字：

**用户名枚举（User Enumeration）**  
通过“错误提示的差异”，批量判断哪些用户名真实存在。

**为什么它值钱**：假设库里有 10 万个账号，攻击者写脚本跑 100 万个常见用户名，把返回“密码错误”的挑出来 —— 就得到了一份**真实用户名单**。之后只针对这份名单爆破，效率提高几十倍。

**记住这个词**，面试和代码审查里都会遇到。

## 三、Q6：这一句说反了
“比如说我们的项目要求用户名**不唯一**”

**反了 —— 我们要求用户名唯一**，否则就不需要加 `uk_username` 了。

你前半段其实说对了（主键管行、唯一索引管字段、数量可以多个），但漏了最关键的对比：

**主键 id 允许两行同名** —— 所以它**根本管不住** username 重复。

一句话补全：

| | **主键 id** | **唯一索引 username** |
| --- | :--- | :--- |
| 保证 | 这一**行**唯一 | 这个**字段**不许重复 |
| 允许同名吗 | **允许**（张三学号 1 和 4 都合法） | **不允许** |

## 四、附加题：帮忙的场景不是“返回前端”
“在从数据库取出数据，返回给前端账号信息的时候帮了我们”

**不完全对。** 返回前端时不带密码，功劳在 `**@JsonProperty(WRITE_ONLY)**`，不是 `@TableField`。

`@TableField(select = false)` 真正帮你的场景是：

**MyBatis 的 SQL 日志不会打出密码列** —— 这是 Task11 你为了“控制台别刷密码”加的。

所以准确的三层分工：

| **注解** | **管什么** | **出问题的场景** |
| :--- | :--- | :--- |
| `@TableField(select=false)` | **查库时不取这一列** | **登录拿不到哈希** ← 这次坑你 |
| `@JsonProperty(WRITE_ONLY)` | **转 JSON 时不输出** | 不影响查库 |
| `@JsonIgnore` | 双向都忽略 | 前端传的密码收不到 |

## 五、你 Q8 那个疑问：登录怕不怕重复提交？
“我们登录貌似不怕提交多次请求吧”

**怕，但不是因为“会出两个账号”。** 三个理由：

**① 白烧 CPU** —— 每次登录要跑 47ms 的 BCrypt。有人一分钟打你 1000 次，就是 47 秒的 CPU，能把小服务器拖死。这是**最容易被利用的 DoS 点**（而且不需要登录成功）。

**② 以后加会话就麻烦了** —— 现在没有 token，重复登录只是多查几次库。但真实系统登录成功要发 token / 写 session，重复提交 = **多个有效会话**，撤销起来很麻烦。

**③ 日志被刷** —— 你那行 `log.warn("登录失败: username=...")`，被人打一万次就是一万行。

**所以 POST 的“不自动重试”依然是对的** —— 不是因为“会重复创建”，是因为“这个动作每执行一次都有成本，不该由中间层擅自替你执行”。
