### 6.1 为什么用 POST
| 方法 | 问题 |
| --- | --- |
| **GET** | 参数必须放 URL：`?username=x&password=y` → **进访问日志、浏览器历史、代理** |
| **PUT** | 隐含“幂等”承诺（发多次结果一样），登录不是 |
| **POST** | 提交数据让服务器处理，**不承诺幂等** ✅ |


### 6.2 幂等到底是什么
**幂等 = 同样的请求发 N 次，服务器的“最终状态”跟发 1 次一样。**

| 请求 | 发 3 次的结果 | 幂等？ |
| --- | --- | --- |
| `POST /user/add` | 库里多 **3 行** | ❌ |
| `PUT /user/update {id:4,...}` | 还是那 **1 行** | ✅ |
| `DELETE /user/delete/4` | 第一次删掉，后两次没事干（状态一致） | ✅ |
| `GET /user/list` | 库不变 | ✅ |


**注意**：幂等不是“返回的文字一样”，是“**状态一样**”。

**这个声明写给谁看** —— 不是给服务器，是给**中间层**（代理、网关、RPC 框架）：它们据此决定“失败后要不要自动重试”。对 POST 绝不自动重试。

### 6.3 为什么入参用 DTO 不用 `User`
| 理由 | 说明 |
| --- | --- |
| 字段更少 | `User` 有 id、createTime，登录根本不需要 —— **能传进来的越少越安全** |
| 避免注解干扰 | `User` 上带着 `@TableField`、`@JsonProperty`，语义会打架 |
| **规则会变** | 密码规则从 6 位改成 8 位时，老用户那些 6 位密码**本来是对的**，不该被登录拦下 |


**最后一条是最容易被忽略的**：**注册是“立规矩”，登录是“认人”**。规矩能变，人不该变。
