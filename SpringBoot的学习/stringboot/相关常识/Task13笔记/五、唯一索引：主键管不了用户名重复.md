### 5.1 撞坑现场
```plain
org.apache.ibatis.exceptions.TooManyResultsException:
Expected one result (or null) to be returned by selectOne(), but found: 2
    at ...UserServiceImpl.login(UserServiceImpl.java:115)
```

库里有**两条 zhangsan**（id=1、id=4）。

### 5.2 这是谁的错？—— 代码没错
`selectOne` 的前提是“一个 username 只有一条”。这个前提**在业务上成立**（用户名不能重复），但**没有任何东西在数据库层保证它**。

代码没错，错的是那个前提没被保证。

### 5.3 主键 vs 唯一索引
| | 主键 `id` | 唯一索引 `uk_username` |
| --- | --- | --- |
| 一张表能有几个 | **只能 1 个** | **可以很多个** |
| 保证什么 | 这一**行**唯一 | 这个**字段**不许重复 |
| 允许同名吗 | ✅ **允许** | ❌ 不允许 |
| 允许 NULL | ❌ | ✅（多个 NULL 不算重复） |


**类比**：主键 = 学号（每人唯一，但允许同名同学）；唯一索引 = “姓名不许重复”的校规。

**关键**：主键管的是“行”，管不了“用户名这个业务字段”。

### 5.4 为什么“直接映射 ID”不行
用户登录只知道自己的名字，**不知道自己是几号**。id 是数据库内部定位行用的，username 才是业务上认人用的。

### 5.5 加索引前必须先清数据
```plain
-- 直接加 → 报错
ALTER TABLE user ADD UNIQUE INDEX uk_username (username);
-- ERROR 1062: Duplicate entry 'zhangsan' for key 'user.uk_username'
```

**唯一索引不是“从今往后不重复”，是“整张表所有数据都必须不重复”。**

所以顺序必须是：**清重复 → 再加索引**。

### 5.6 两道防线，分工不同
```plain
请求 → ① 应用层检查（先查重名）→ 有 → 409「用户名已存在」（友好提示）
              ↓ 没有
        ② 数据库唯一索引 → 有 → 1062（兜底）
```

**为什么两道都要**：第①道会被**并发**绕过。

```plain
请求A：查 zhangsan 不存在 →（还没插）
请求B：查 zhangsan 不存在 →（也通过）
请求A：插入 ✅
请求B：插入 ← 数据库拒了
```

**唯一索引的真正价值**：不是“规范要求”，是**在代码判断被并发击穿的瞬间兜底**。

⚠️ **遗留问题**：并发被拒的那个请求抛 `DuplicateKeyException`，不是 `BusinessException` → 会走 500，用户看到“系统繁忙”。真实项目要加一个 handler 转成 409。
