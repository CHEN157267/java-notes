代码里：`insert` 返回 0 抛 `IllegalStateException`；`updateById` 返回 0 抛 `BusinessException`。**为什么不统一？**

| | `BusinessException`（业务） | `IllegalStateException`（系统） |
| --- | --- | --- |
| **为什么是这个** | "0" 有明确业务含义（这行不存在） | "0" **没有**业务解释（校验过了、名字也不重，却插不进 → 意料之外） |
| **走哪个 handler** | `handleBusinessException` | `Exception` 兜底 |
| **返回给前端的 code** | 409 / 404（**有含义**） | 500（+ "系统繁忙"） |
| **日志级别** | `log.warn`（**预期内**，别惊动运维） | `log.error`（**需人介入**，要告警） |
| **谁该关心** | **用户**能看懂、能应对 | **开发 / 运维**去看堆栈 |


**分界线（一句话）**：

**这个失败，能不能用"业务语言"向用户解释清楚？** 能 → 业务异常（转 4xx）；不能 → 系统异常（500 + 日志）。

## 九、接口设计：`id 从哪来` 决定要不要判存在
| id 来源 | 要不要判存在 | 例子 |
| --- | --- | --- |
| **登录态**（后端自己取，前端不传） | ❌ 不用 | `PUT /user/profile`、`PUT /user/password`、`DELETE /user/me` |
| **前端传的参数** | ✅ 必须判 | 后台/管理员改任意用户：`PUT /admin/user/{id}` |


现在这个带 id 的 `PUT /user/update`，**语义上更像「管理员接口」**（能改**任意**用户）——因为项目还没有登录系统，只能让前端把 id 传进来。等以后真加登录，这段会自然分成"我的资料"和"管理用户"两个接口。

**未登录状态能做的两件核心事 = 注册 + 登录。**

⚠️ 注意：**改密码同样必须登录**（否则谁知道改谁的密码）。唯一例外 = **忘记密码**，它靠邮箱/短信验证码**先验证身份**，用"验证身份"顶替了"登录"。
