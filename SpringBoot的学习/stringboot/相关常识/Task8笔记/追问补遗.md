### ① 解耦：目标 vs 手段（含"食堂送菜"类比）
三个词要分清：

| 词 | 是什么 | 一句话 |
| --- | --- | --- |
| **耦合** | 状态 | A 有多需要**知道** B 的细节（知道越多越动不得） |
| **解耦** | **目标** | 让 A **不必知道** B 的细节 |
| **接口 / 抽象 / 统一结构** | **手段** | 达到解耦的常见做法 |


⚠️ 常见误解：把"解耦"理解成"像解密那样把一个东西拆开"。那是**解密/破解**，跟解耦无关。_解耦是__**降低依赖**__，不是"拆开某个加密物"。_

**本项目的实例**：Service 抛 `BusinessException` 时，它**不知道**"这会被转成 `Result.code=404`、HTTP 会回 200"。它只报告事实。 → 哪天要把响应体从 `Result` 换成别的结构，**Service 一行都不用改**，只改 handler。 → 反例：若 Service 里直接 `return Result.error(404, "...")`，那 Service 就同时绑上了三样：`Result` 的结构、404 的业务含义、HTTP 怎么回。

**类比（食堂送菜）** —— 成立，补完整：

| 类比 | 对应 |
| --- | --- |
| 送菜的人 | **Service** —— 只把"事实"送过来（菜是坏的 / 用户不存在） |
| 食堂大叔大妈 | **handler** —— 决定这菜怎么处理（炒 / 退 / 报 404） |
| 最终端出的饭 | `**Result**` —— 送到前端手上的东西 |


送菜的人**不关心最后做成什么菜**，这就是解耦。再补一层：他"送的是菜还是肉"（抛 404 还是 409）也只是**报告事实**，仍然不是"决定菜单"。

### ② "JVM 能抛异常，为什么还要自己 throw"
因为：**JVM 只认识"程序出错"，不认识"业务语义"。**

+ `selectCount(username) == 1` → JVM 眼里这是一次**完全正常**的查询，返回 1 天经地义，它没理由抛；
+ `updateById` 返回 0 → SQL **执行成功了**，JVM 觉得一切正常，也没理由抛。

只有**你**知道"返回 1 = 重名 = 该 409"、"返回 0 = 用户不存在 = 该 404"。

**一句话：「出错」是 JVM 的判断，「失败」是你的判断。**

### ③ `throws` 是"空头支票"〔实测〕
```plain
void onlyThrows() throws IOException {   // 方法体里没有任何会抛 IOException 的代码
    System.out.println("nothing");
}
```

〔实测 JDK 21〕**编译通过，exit code 0**。

→ 所以"**全是 **`**throws**`**、没有 **`**throw**`"**不等于**"JVM 会抛"——也可能**压根没人抛**，什么都不会发生。 → `throws` 只负责挂招牌，**它自己一个异常都产生不了**。（真正抛的时刻，永远在某个 `throw`，或 JVM/框架内部。）

### ④ 三个默认解析器的真实顺序（补 §四）〔原文引用：`DispatcherServlet.properties`〕
```plain
ExceptionHandlerExceptionResolver      ← 我们的 @ExceptionHandler 归它管，排第 1
ResponseStatusExceptionResolver
DefaultHandlerExceptionResolver        ← "框架原本干活的"，排第 3
```

**三个都没有显式 order**（`AbstractHandlerExceptionResolver` 初始即 `LOWEST_PRECEDENCE`）→ 真实顺序来自 **properties 的声明顺序 + 稳定排序**，**不是**靠 order 数值各不相同。别再讲成"order 排前面所以先执行"。

**补一问：完全没写 advice 时谁接？** → `DefaultHandlerExceptionResolver` 只翻译它**认识**的框架异常（405/415/静态资源等）；它不认识的继续往外走 → Spring Boot 的 `/error` → **那张默认错误页**。（Task5 的 DB 密码事故就是这条"没人接"的路。）

### ⑤ 三种「状态码方案」对比（补 §五）
| 方案 | HTTP | body.code | 前端判几处 | 基础设施能看到失败吗 |
| --- | --- | --- | --- | --- |
| **A（我们 API 层现状）** | 恒 200 | 承载全部语义 | **1 处**（只看 body.code） | ❌ 看不见 |
| **B（统一映射）** | 如实 | 与 HTTP **对齐** | **1 处**（只看 HTTP） | ✅ 看得见 |
| **C（不一致、无规律）** | 时而如实时而 200 | 与 HTTP 无规律 | **2 处** | 不可预期 |


**★ 关键纠正：是 C 需要"判两次"，不是 B。** "统一映射"恰恰是**用来消掉"判两次"的**（两个码对齐 → 看哪个都一样）。

**★ 口径收窄（追问后修正，我原话"一旦不全用……这就是乱"说过头了）**：

我们项目其实是**分层整齐**的：

+ **我们自己的 API**（`/user/**`、`/v3/api-docs`）→ **100% 是 **`**200 + body.code**`，规则单一、无例外；
+ **非 API 的静态资源**（favicon）→ 走 HTTP 404，而它**不在我们的接口清单里**，**前端也不会主动调它**。

→ 所以这不是"乱"，是"**两层各用一套规则**"；对前端来说实际**只有一条通道**（body.code）。 → 真正会乱的是**在同一类接口内部**没规律（例：`/user/add` 重名回真 409、`/user/update` 重名却回 `200+code 409`）——**我们没这个问题**。

### ⑥ `api` 的三个语境（是同一个意思）
共同定义：**API = 一方向另一方提供的"可调用的接口"**，区别只在"被调用的东西是什么"。

| 说法 | 谁提供 | 你调用的是什么 | 例 |
| --- | --- | --- | --- |
| Java API 文档 | JDK / 库作者 | 类和方法 | `List.add()` |
| API Key | 某个在线服务商 | 对方服务器上的 **HTTP 接口** | DeepSeek `/chat/completions` |
| 我们项目的 API | **你自己** | 你后端暴露的 **HTTP 接口** | `/user/list` |


→ "favicon **不是我们的 API**" = 它不在我们**对外承诺的接口清单**里，是浏览器自己要一个静态文件。 → 连到 Task9：**你调别人的 API**（DeepSeek）；**你项目里的 **`**/ai/chat**`** 是你提供给别人（前端）的 API**。同一个词，两个方向。

### ⑦ `@ResponseStatus` 与 `NoResourceFoundException`（补 §五⑤ / §七）
猜测："是不是这个异常类上**本来就**贴了 `@ResponseStatus`？"

〔原文引用：`spring-webmvc-6.2.19` 源码包〕

```plain
@SuppressWarnings("serial")
public class NoResourceFoundException extends ServletException implements ErrorResponse {
```

+ 类声明上方**只有 **`**@SuppressWarnings**`，**没有 **`**@ResponseStatus**`（整个文件里 "ResponseStatus" 出现 **0 次**）。
+ 它"自带 404"靠的是**另一条机制**：`implements ErrorResponse` + `getStatusCode()` 返回 `HttpStatus.NOT_FOUND`（构造器里 `ProblemDetail.forStatusAndDetail(getStatusCode(), ...)`），再由 `DefaultHandlerExceptionResolver` 的专门分支翻译成 **HTTP 404**（日志只打 debug）。
+ **我们自己那个 404**，是后来贴在 **handler 方法**上的 `@ResponseStatus(HttpStatus.NOT_FOUND)` —— 位置不同、机制不同，**结果一样**。
+ 官方警告仍在：贴在**异常类**上、或设了 `reason` → 走 `sendError` → 容器丢 **HTML 错误页**，"**unsuitable for REST APIs**"。我们没踩（贴方法 + 无 reason）。

### ⑧ 想自己验证？三条路
1. **空头支票**：建个类写 `void f() throws java.io.IOException {}`，`javac` 一下 —— 不报错。
2. **JVM 抛的也归 advice 管**：临时加 `@ExceptionHandler(NullPointerException.class)`，在某接口里故意 `String s = null; s.length();`，看是不是被自己的 handler 接住。
3. **类上确实没注解**：IDEA 里 `Ctrl+N` 搜 `NoResourceFoundException`，看类声明上方有没有 `@ResponseStatus`。
